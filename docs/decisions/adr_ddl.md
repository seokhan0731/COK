# ADR 004: 하이버네이트 ddl update 현행 유지

## 개요

* **날짜:** 2026.11.04
* **작성자:** 김석환

## 컨텍스트

* **배경:**  
  배포 사전 작업 중 DB 초기화가 세 군데로 나뉘어 있음을 확인

| 대상                        | 위치                                             | 시점        |
  |---------------------------|------------------------------------------------|-----------|
| `CREATE EXTENSION vector` | `docker/initdb/`                               | 컨테이너 첫 기동 |
| 테이블                       | Hibernate                                      | Spring 기동 |
| 기준 데이터                    | `data.sql` (`defer-datasource-initialization`) | 테이블 생성 직후 |

* **요구 사항:**
* 컨테이너를 반복 기동해도 동일한 결과 도출
* 배포 범위를 늘리지 않을 것

## 결정

* `ddl-auto: update` 구조를 유지하고, 별도 Flyway 등 마이그레이션 도구로 전환 X
    1. 남은 작업 범위에 기능 추가가 없어 엔티티 변경이 예정되어 있지 않아. update의 위험은 엔티티가 반복 수정되며 테이블에 누적되는 것인데, 그 조건 자체가 성립하지 않는다.

## 기대 효과

* **추가 작업 발생 X:** 배포 완료라는 목표에 필요한 작업만 수행하여 중단 위험을 낮춘다.

## 감수 비용

## 감수하는 비용

* `ddl-auto: update` 는 컬럼 삭제와 타입 변경을 수행하지 않는다. 따라서 엔티티를 반복
  수정한 환경과 빈 DB에서 새로 생성한 환경의 스키마가 일치한다는 보장이 없으며, 적용된
  DDL이 레포에 남지 않아 리뷰와 롤백이 불가능하다.
* 엔티티 변경이 재개되거나 운영 환경이 둘 이상으로 늘어나면 재검토한다.
